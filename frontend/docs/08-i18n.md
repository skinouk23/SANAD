# 08 — Internationalization (i18n)

## Overview

The frontend uses a custom typed-dictionary i18n system. There is no runtime library such as `react-i18next`.

Current code locations:

- translation contract: `src/i18n/types.ts`
- translation source files: `src/i18n/translations/*.ts`
- source export barrel: `src/i18n/index.ts`
- language metadata and fallback definition: `src/shared/lib/i18n/languages.ts`
- single runtime locale registry, cache, and default loader: `src/shared/lib/i18n/locale-loader.ts`
- boot-time preload: `src/app/bootstrap/runtime.ts` and `src/index.tsx`
- React provider and hook: `src/shared/lib/i18n/language-context.tsx`
- compatibility re-export: `src/contexts/LanguageContext.tsx`

`src/i18n/default-locale/*` no longer exists. The old alias/default-locale wrapper path was removed, and runtime translation loading now has a single owner in `src/shared/lib/i18n/locale-loader.ts`.

## Supported Locales

| Code | Language | Direction | Translation source | Notes |
| --- | --- | --- | --- | --- |
| `fr-FR` | Français | LTR | `src/i18n/translations/fr.ts` | Fallback locale and current default when no env override is provided |
| `en-GB` | English | LTR | `src/i18n/translations/en.ts` | Full dictionary |
| `ar-TN` | العربية | RTL | `src/i18n/translations/ar.ts` | Only RTL locale |
| `de-DE` | Deutsch | LTR | `src/i18n/translations/de.ts` | Built by spreading English and overriding German strings |
| `nl-NL` | Nederlands | LTR | `src/i18n/translations/nl.ts` | Full dictionary |

The source of truth for locale metadata is `src/shared/lib/i18n/languages.ts`, not the older `src/contexts` compatibility file.

## Runtime Ownership

`src/shared/lib/i18n/locale-loader.ts` is now the single runtime owner for locale loading.

- `translationLoaders` contains the runtime registry for every supported `LanguageCode`
- `resolveDefaultLanguageCode()` reads `env.DEFAULT_LOCALE` and falls back to `FALLBACK_LANGUAGE_CODE` (`fr-FR`) when needed
- `loadTranslations(code)` is the shared runtime path for loading dictionaries
- `translationCache` stores loaded dictionaries by language code
- `translationRequests` deduplicates concurrent requests for the same locale
- `LanguageProvider` and bootstrap code both use this loader instead of importing a special default-locale wrapper

`src/i18n/index.ts` is not the runtime registry. It is only a source export barrel and does not define the app's supported-locale runtime behavior.

## Boot-Time Locale Preload

The active locale is now resolved and preloaded during application bootstrap instead of being corrected inside `LanguageProvider` after mount.

- `initializeRuntime()` resolves the initial language code through `resolveInitialLanguageCode()`
- bootstrap applies that code to `document.documentElement` before React renders so first paint uses the correct `lang` and `dir`
- bootstrap then loads the matching translations through `loadI18nState(code)`
- `src/index.tsx` passes the resulting `initialI18nState` into `App`
- `AppProviders` then passes that state into `LanguageProvider`
- the active locale is already loaded and applied on the first render without a post-mount storage correction pass

## Lazy Locale Loading

Non-default locales are still loaded on demand, but they now use the same runtime loader path as the default locale.

`src/shared/lib/i18n/locale-loader.ts` currently:

- keeps a `translationLoaders` map of dynamic `import(...)` functions
- caches loaded dictionaries in an in-memory `Map<LanguageCode, TranslationKeys>`
- deduplicates concurrent loads in a `Map<LanguageCode, Promise<TranslationKeys>>`
- returns cached translations on repeat selections
- falls back to the resolved default loader when no loader exists for a requested code

`LanguageProvider` then applies those dictionaries asynchronously.

Current provider behavior:

- starts from the bootstrapped `initialI18nState`
- does not re-read storage to correct locale during mount; bootstrap owns initial locale selection
- uses a `requestIdRef` guard so late async loads cannot overwrite a newer selection
- applies changes inside `startTransition(...)`
- persists new user-initiated language changes to `localStorage` key `language`
- keeps the current locale active if a lazy translation chunk fails to load

## DOM and Direction Handling

`LanguageProvider` updates the root document whenever the active language changes.

- `document.documentElement.lang` is set to the active locale code
- `document.documentElement.dir` is set to `ltr` or `rtl`
- `ar-TN` is the only locale that currently switches the app into RTL mode

Shared UI can consume the same direction value through `useLanguage()`. For example, `AppToaster` uses `dir` to flip toast placement between left and right.

## Test Contract

Tests and isolated mounts should follow the same bootstrap-driven contract as the runtime app.

- mount `LanguageProvider` only with an explicit `initialI18nState`
- apply the same locale to `document.documentElement` before rendering when test formatting or other document-based locale reads matter
- use `renderWithProviders(ui, { locale: 'en-GB' })` for common cases
- use `renderWithProviders(ui, { initialI18nState })` when a test needs a fully custom translation payload
- use `bootstrapTestI18n({ locale })` when wiring `LanguageProvider` manually outside `renderWithProviders`
- do not rely on ambient `localStorage` as the primary locale source in tests or stories
- when a narrow test needs to mock the hook directly, mock `@/shared/lib/i18n/language-context`, not `@/contexts/LanguageContext`

## Translation Authoring Rules

The translation contract remains `TranslationKeys` in `src/i18n/types.ts`.

Current authoring rules:

- every translation file exports a plain TypeScript object typed as `TranslationKeys`
- runtime loading happens through `src/shared/lib/i18n/locale-loader.ts`, not through `src/i18n/index.ts`
- when adding a locale, update both `src/shared/lib/i18n/languages.ts` and the `translationLoaders` registry in `src/shared/lib/i18n/locale-loader.ts`
- German is no longer inline in the context provider; it lives in `src/i18n/translations/de.ts`
- interpolation is still manual at call sites because the current system does not provide a message-formatting runtime
